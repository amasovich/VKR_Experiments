# Журнал инженерных решений

## DEC-001. Основной рабочий каталог экспериментов

Решение: создать основной каталог экспериментальной части на инженерной машине Windows.

Путь:
D:\HOME_BASE\VKR_Experiments

Обоснование:
- инженерная машина используется как центральная нода подготовки, обработки и архивирования данных;
- mini-PC используется как узел исполнения vPLC;
- хранение основного архива на инженерной машине упрощает обработку, резервное копирование и подготовку материалов для ВКР.

Статус: принято.

## DEC-003. Роль VPLC Server в первых экспериментальных сериях

Решение: VPLC Server фиксируется как установленный и проверенный компонент стенда, но не включается в первый baseline-контур измерений детерминизма и стабильности цикла VPLC.

Для первых серий основной объект измерения:

```text
VPLC runtime на VPLC_HOST
```

VPLC Server используется позднее только для расширенных сценариев, если потребуется оценить влияние коммуникационного слоя, OPC UA, внешних клиентов или сетевого обмена.

Обоснование:
- первый baseline должен измерять поведение VPLC runtime с минимальным числом внешних факторов;
- включение VPLC Server добавляет коммуникационный слой и усложняет интерпретацию причин джиттера;
- контейнеризация VPLC Server до получения baseline VPLC runtime может смешать эффекты runtime, сервера, сети и контейнерной среды;
- установленный VPLC Server остаётся доступным для последующих режимов, но его запуск и контейнеризация выполняются отдельным решением.

Следствие:
- пункт проверки VPLC Server в Linux CLI считается выполненным как инфраструктурная проверка;
- для первых тестовых проектов и baseline-прогонов VPLC Server остаётся остановленным, если не потребуется явно;
- контейнерный профиль сначала проектируется для VPLC runtime, а VPLC Server добавляется только в расширенном сценарии.

Статус: принято.

## DEC-002. Порядок проверки VPLC перед контейнеризацией

Решение: перед реализацией контейнерного профиля Podman выполнить штатную функциональную проверку VPLC в bare-metal Linux CLI-режиме совместно с VPLC Studio на инженерной машине Windows.

Принятый порядок:
1. подтвердить установку и CLI-доступность VPLC / VPLC Server на `VPLC_HOST`;
2. установить или запустить VPLC Studio на `ENG_NODE`;
3. проверить подключение VPLC Studio к `VPLC_HOST`;
4. создать минимальный тестовый проект VPLC;
5. загрузить и запустить проект на VPLC;
6. зафиксировать изменения статуса, конфигурации, тегов, программы и логов;
7. только после понимания штатного workflow переходить к контейнерному профилю Podman.

Обоснование:
- контейнеризировать компонент, который ещё не проверен в штатном пользовательском сценарии, методически рискованно;
- перед упаковкой в контейнер нужно понять, какие файлы проекта, сервисы, порты, состояния и журналы реально используются VPLC / VPLC Server;
- такой порядок лучше сохраняет трассируемость и снижает риск ошибочной интерпретации проблем контейнера как проблем VPLC.

Следствие для этапа 4.0:
- пункт 10 "Реализовать контейнерный профиль запуска через Podman" выполняется после функциональной проверки VPLC Studio и минимального проекта;
- пункт 11 "Создать минимальный тестовый проект VPLC" фактически становится ближайшим рабочим шагом после CLI-проверки VPLC.

Статус: принято.
