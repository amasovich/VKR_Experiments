# Siemens S7-1200 SCL sources for VKR workload v0.2

Дата подготовки: 2026-05-02.

## Назначение

Папка содержит черновые external source файлы для TIA Portal V20:

```text
DB_VKR_S7_Run.scl
OB123_VKR_WorkloadCycle.scl
```

Они предназначены для обсуждения, импорта и последующей проверки в проекте Siemens S7-1200. Файлы не являются результатом экспериментального прогона и не содержат KPI.

## Принятая структура

- основной цикл Siemens: обычный cyclic OB `OB123_VKR_WorkloadCycle`;
- источник периода: `RD_LOC_T().NANOSECOND`;
- `Tper_ms`: разница tick start-to-start между соседними вызовами OB;
- `Jper_ms`: `Tper_ms - T0_ms`;
- `deadline_miss`: `Tper_ms > deadline_threshold_ms`;
- workload и логирование находятся прямо в OB;
- состояние, параметры и кольцевой буфер находятся в одном DB `DB_VKR_S7_Run`.
- `freeze_logging` замораживает запись в `Log.rows` для ручного snapshot;
- `reset_log_request` одноразово сбрасывает счетчики, workload-состояние и индексы кольцевого лога.

## Параметры по умолчанию

```text
T0_ms = 100.0
deadline_threshold_ms = 100.0
max_valid_tper_ms = 1000.0
log_capacity = 1000
load_level = 0
load_passes_level1 = 32
load_passes_level2 = 128
load_passes_level3 = 512
max_load_passes = 512
freeze_logging = FALSE
reset_log_request = FALSE
```

Эти значения нужны для технической проверки цепочки артефактов. Они не являются финальными методическими порогами GREEN / YELLOW / RED.

## Ступени нагрузки

`load_level` задает ступень нагрузки без изменения SCL-кода:

```text
0 = idle, только счетчики, heartbeat, диагностика и логирование
1 = легкая нагрузка, 32 прохода по int_state[0..15]
2 = средняя нагрузка, 128 проходов по int_state[0..15]
3 = высокая нагрузка, 512 проходов по int_state[0..15]
```

Количество проходов на уровнях `1..3` задается параметрами `load_passes_level1..3` и ограничивается `max_load_passes`. Значения можно уточнять после коротких TECH-проверок на фактической CPU, но для сопоставления Siemens/VPLC выбранные значения должны фиксироваться в `ModeID`/`ManifestCfg`.

## Зафиксированные HW PLC Mode

```text
S7_L0_IDLE_10_20    load_level=0, load_passes=0,   T0_ms=10, deadline_threshold_ms=20
S7_L1_LIGHT_10_20   load_level=1, load_passes=32,  T0_ms=10, deadline_threshold_ms=20
S7_L2_MEDIUM_25_35  load_level=2, load_passes=128, T0_ms=25, deadline_threshold_ms=35
S7_L3_HIGH_75_100   load_level=3, load_passes=512, T0_ms=75, deadline_threshold_ms=100
S7_L3_STRESS_75_80  load_level=3, load_passes=512, T0_ms=75, deadline_threshold_ms=80
```

Для каждого режима перед snapshot нужно установить соответствующие значения в `Config`, выполнить reset, дождаться полного заполнения кольцевого буфера и только затем включить `freeze_logging`.

## Ручной snapshot DB

Для технического снимка через TIA Portal рекомендуется:

1. Задать `Config.reset_log_request := TRUE`.
2. Дождаться автоматического возврата `reset_log_request` в `FALSE`.
3. Задать нужные `T0_ms`, `deadline_threshold_ms`, `load_level`.
4. Дождаться заполнения буфера: `State.buffer_wrapped = TRUE` или нужного `sample_index`.
5. Задать `Config.freeze_logging := TRUE`.
6. Убедиться, что `State.write_index` и `State.sample_index` перестали меняться.
7. Сохранить DB snapshot.
8. После снимка вернуть `Config.freeze_logging := FALSE` или выполнить новый reset перед следующим прогоном.

Такой snapshot остается ручным, но массив `Log.rows` не меняется во время сохранения. После reset старые строки физически не очищаются; для чистого снимка нужно дождаться `State.buffer_wrapped = TRUE`, чтобы все 1000 строк были перезаписаны новым прогоном.

## Порядок проверки в TIA Portal

1. Импортировать `DB_VKR_S7_Run.scl`.
2. Импортировать `OB123_VKR_WorkloadCycle.scl`.
3. Убедиться, что блок импортирован как обычный cyclic OB и вызывается циклическим исполнением CPU.
4. Скомпилировать проект и исправить возможные синтаксические отличия TIA/SCL.
5. Выполнить короткий TECH-прогон только для проверки `DB`-буфера и последующего экспорта `RawLogs`.

## Ограничения

- Синтаксис должен быть проверен в TIA Portal на фактической CPU 1215C.
- `RD_LOC_T().NANOSECOND` принят как кандидат на источник времени для TECH-прогона, потому что `TIME_TCK()` не поддерживается текущей CPU/библиотекой.
- Расчёт по `NANOSECOND` корректен для соседних вызовов cyclic OB с ожидаемым интервалом меньше одной секунды; для порога `100 ms` это допустимо для технической проверки.
- Первую строку буфера нужно считать невалидной по времени, так как для неё ещё нет предыдущего tick.
- При изменении `log_capacity` нужно согласовать его с фактическим размером массива `Log.rows`.
- Размер 1000 строк выбран как консервативный старт для импорта и короткой TECH-проверки; длительный буфер согласуется отдельно.
- Сброс `reset_log_request` не очищает 1000 строк в одном цикле, чтобы не создавать лишний всплеск времени цикла; валидным считается буфер после полного перезаполнения.
- Для финальных хвостовых метрик 1000 строк являются нижней границей; предпочтительны повторные серии или расширенный/потоковый метод съёма после проверки памяти PLC.
