# План прикладной нагрузки и съёма метрик

## Назначение

Документ фиксирует, что должно быть подготовлено перед первым коротким прогоном этапа 4.0: сопоставимые прикладные программы нагрузки для `vPLC_container` и `HW_PLC`, а также единая схема регистрации сырых данных и расчёта KPI.

Экспериментальные значения, KPI и выводы в этом документе не приводятся.

## Методическая основа

По методике ВКР сравнение аппаратного PLC и vPLC допустимо только в пределах одного режима `Mode`: одинаковый сценарий, одинаковый номинальный период цикла, одинаковый профиль нагрузки, одинаковая длительность серии и одинаковая логика регистрации артефактов.

Минимальная цепочка трассируемости:

```text
ModeID -> RunID -> configuration snapshot -> RawLogs -> processed tables -> summary card
```

Ключевые требования к подготовке:

- сопоставимость условий для `HW_PLC` и `vPLC_container`;
- воспроизводимость режима и параметров запуска;
- сохранение сырых данных без ручной правки;
- отделение инфраструктурных smoke-test от экспериментальных прогонов;
- отсутствие вычисленных KPI до появления фактических `RawLogs`.

## Прикладная workload-программа

Цель workload-программы — создать одинаковую по смыслу циклическую нагрузку для VPLC и S7-1200, пригодную для baseline/stress серий.

Машинно-читаемый черновик профиля:

```text
configs\workload_profile_v0.yaml
```

Предварительная структура одного цикла:

1. увеличить счётчик цикла;
2. выполнить фиксированный набор целочисленных операций;
3. выполнить фиксированный набор булевых операций;
4. выполнить фиксированный проход по небольшому массиву или набору однотипных переменных;
5. обновить контрольную сумму / аккумулятор результата;
6. обновить диагностические переменные, доступные для мониторинга.

Ограничения:

- не использовать случайные величины;
- не использовать внешние сетевые обращения внутри workload;
- не использовать ручные действия оператора как часть цикла;
- не смешивать в одном baseline-режиме workload и искусственный stress, если stress не описан в `Mode`.

## Workload v0

Статус: `draft_siemens_source_v0_2_pre_vplc_alignment`.

Workload v0 описывает семантику, а не финальный синтаксис VPLC ST или Siemens SCL/ST. Если одна из сред не поддержит массивы в нужном виде, допускается заменить массивы набором однотипных переменных при сохранении порядка операций.

Псевдокод одного цикла:

```text
cycle_counter := cycle_counter + 1

heartbeat_divider := heartbeat_divider + 1
IF heartbeat_divider >= heartbeat_divisor_cycles THEN
    heartbeat := NOT heartbeat
    heartbeat_divider := 0
END_IF

IF load_level NOT IN allowed_load_levels THEN
    error_flag := TRUE
    effective_load_level := 0
    load_passes := 0
ELSE
    effective_load_level := load_level
    load_passes := passes_for_load_level(load_level)
END_IF

workload_accumulator := (workload_accumulator + cycle_counter + effective_load_level) MOD accumulator_modulus

IF load_passes > 0 THEN
    FOR p := 1 TO load_passes DO
        FOR i := 0 TO work_items - 1 DO
            int_state[i] := (int_state[i] + cycle_counter + i + p + effective_load_level) MOD accumulator_modulus
            bool_state[i] := (int_state[i] MOD 2) = 0
            IF bool_state[i] THEN
                workload_accumulator := (workload_accumulator + int_state[i]) MOD accumulator_modulus
            ELSE
                workload_accumulator := (workload_accumulator + i + p) MOD accumulator_modulus
            END_IF
        END_FOR
    END_FOR
END_IF
```

Черновые константы:

| Параметр | Значение | Назначение |
|---|---:|---|
| `work_items` | 16 | число однотипных операций состояния |
| `load_passes_level1` | 32 | число проходов для лёгкой нагрузки |
| `load_passes_level2` | 128 | число проходов для средней нагрузки |
| `load_passes_level3` | 512 | число проходов для высокой нагрузки |
| `max_load_passes` | 512 | защитное ограничение числа проходов |
| `heartbeat_divisor_cycles` | 100 | период переключения диагностического бита в циклах |
| `accumulator_modulus` | 2147483647 | ограничение аккумулятора для сопоставимого переполнения |

Черновые уровни нагрузки:

| `load_level` | Сценарий | Смысл |
|---:|---|---|
| 0 | `idle_cycle` | минимальная циклическая диагностика: счётчик, heartbeat, accumulator |
| 1 | `workload_cycle_light` | детерминированная целочисленная/булева нагрузка, 32 прохода по состоянию |
| 2 | `workload_cycle_medium` | та же семантика, 128 проходов по состоянию |
| 3 | `workload_cycle_high` | та же семантика, 512 проходов по состоянию |

## Рабочие Mode для HW PLC S7-1200

После технической калибровки Siemens S7-1200 зафиксирован первый набор HW PLC режимов:

| `ModeID` | `load_level` | `load_passes` | `T0_ms` | `deadline_threshold_ms` | Назначение |
|---|---:|---:|---:|---:|---|
| `S7_L0_IDLE_10_20` | 0 | 0 | 10 | 20 | baseline без прикладной нагрузки |
| `S7_L1_LIGHT_10_20` | 1 | 32 | 10 | 20 | лёгкая нагрузка |
| `S7_L2_MEDIUM_25_35` | 2 | 128 | 25 | 35 | средняя нагрузка |
| `S7_L3_HIGH_75_100` | 3 | 512 | 75 | 100 | высокая нагрузка с рабочим запасом по deadline |
| `S7_L3_STRESS_75_80` | 3 | 512 | 75 | 80 | предельный stress-режим |

Эти режимы сначала используются для HW PLC, затем для сопоставления должны быть зеркально реализованы на VPLC с теми же `T0_ms`, `deadline_threshold_ms`, `load_level`, `load_passes` и процедурой съёма данных.

Текущий кольцевой буфер `Log.rows[0..999]` достаточен для первого технического съёма HW PLC и проверки цепочки артефактов. Для финальных KPI, особенно `Q99.9` и `Lburst`, 1000 строк являются нижней границей: предпочтительны несколько серий по 1000 строк или отдельное увеличение/потоковый съём после проверки памяти PLC и метода экспорта.

Значения `Tper`, `Jper` и `deadline_miss` не вычисляются внутри workload-программы без подтверждённого источника времени. Workload только формирует наблюдаемые диагностические переменные.

## Черновая карта переменных

Обязательные переменные:

| Переменная | Назначение |
|---|---|
| `cycle_counter` | монотонный счётчик выполненных циклов |
| `heartbeat` | периодически изменяемый диагностический бит |
| `workload_accumulator` | контрольная сумма результата вычислений |
| `load_level` | идентификатор уровня нагрузки, если выбран параметризованный вариант |
| `load_passes` | фактическое число проходов нагрузки для строки или режима |
| `error_flag` | признак внутренней ошибки workload-логики, не признак экспериментального deadline miss |

Переменные времени цикла и deadline miss не должны придумываться программой без подтверждённого источника времени. Если платформа не даёт корректный timestamp внутри цикла, эти поля рассчитываются внешней процедурой съёма данных или помечаются как недоступные для конкретного метода.

## RawLogs

Машинно-читаемый черновик схемы:

```text
configs\rawlogs_schema_cycle_v0.yaml
```

Минимальный формат для логов цикла:

| Поле | Смысл |
|---|---|
| `run_id` | идентификатор прогона |
| `mode_id` | идентификатор режима |
| `series_id` | идентификатор серии |
| `cycle_index` | номер цикла или номер наблюдения |
| `ts_start` | timestamp начала цикла / наблюдения, если доступен |
| `ts_end` | timestamp конца цикла / наблюдения, если доступен |
| `timestamp_tick_ns` | платформенный tick в нс, если доступен; для Siemens RD_LOC_T это `NANOSECOND`, не полный wall-clock timestamp |
| `Tper` | фактический период / измеренная длительность периода |
| `Jper` | отклонение от номинального периода |
| `deadline_miss` | признак превышения допустимого порога |
| `deadline_threshold_ms` | порог, по которому вычислен `deadline_miss` |
| `load_level` | уровень нагрузки |
| `load_passes` | фактическое число проходов нагрузки |
| `notes` | служебная пометка без ручного редактирования исходных данных |

Если первое измерение будет технической проверкой логирования, а не полноценным экспериментом, это явно указывается в `RunID` и summary card.

RawLogs v0 расширяет минимальный формат служебными полями:

- `object` — ветвь измерения: `HW_PLC` или `vPLC_container`;
- `node_id` — узел, сформировавший или собравший строку;
- `sample_index` — монотонный номер строки наблюдения;
- `ts_observe` — timestamp наблюдения со стороны источника или сборщика;
- `timestamp_tick_ns` — внутренний tick источника, если доступен;
- `timestamp_source` — источник временной базы: `plc_internal`, `plc_internal_rd_loc_t_nanosecond`, `vplc_internal`, `eng_node_poll`, `host_log`, `unavailable`;
- `quality_flag` — признак качества строки: `ok`, `technical_check`, `missing_timestamp`, `derived_from_polling`, `invalid_row`, `excluded_from_processing`.

Для ручного snapshot Siemens DB в версии SCL v0.2 используется `Config.freeze_logging`: перед сохранением снимка запись в `Log.rows` замораживается, после сохранения флаг возвращается в `FALSE`. Сброс между техническими проверками выполняется одноразовым флагом `Config.reset_log_request`; после сброса нужно дождаться `State.buffer_wrapped = TRUE`, чтобы старые строки были перезаписаны новым прогоном.

Политика timestamp:

- прямые timestamp цикла предпочтительнее внешнего polling;
- расчёт `Tper` по внешнему polling допускается только после отдельной проверки метода;
- если корректная временная база не подтверждена, поля `ts_start`, `ts_end`, `Tper`, `Jper`, `deadline_miss` остаются пустыми;
- строки технической проверки логирования могут проверять цепочку артефактов, но не используются для экспериментальных KPI.

## Правила идентификаторов

Черновые правила именования:

```text
SeriesID = SER_<YYYYMMDD>_<MODEID>_SNN
RunID    = RUN_<YYYYMMDD>_<MODEID>_SNN_RNN
```

Для технической проверки логирования добавляется суффикс:

```text
RUN_<YYYYMMDD>_<MODEID>_SNN_RNN_TECH
```

Пример является только шаблоном, а не фактическим прогоном:

```text
SER_20260502_C1_VPLC_20_IDLE_REPEAT_S01
RUN_20260502_C1_VPLC_20_IDLE_REPEAT_S01_R01_TECH
```

`ModeID` берётся из `configs\mode_matrix.yaml`. Если перед первым коротким прогоном появится отдельный технический режим проверки логирования, он должен быть добавлен в матрицу до запуска.

## KPI после обработки

После получения фактических `RawLogs` рассчитываются:

- `min(Tper)`;
- `max(Tper)`;
- `median(Tper)`;
- `Q95(Tper)`;
- `Q99(Tper)`;
- `Q99.9(Tper)`;
- `Rmiss`;
- `Lburst`;
- `DQ99`;
- показатели повторяемости между сериями.

Метрика реакции `Tresp` добавляется только если будет подтверждён корректный способ генерации входного события и фиксации выходной реакции для обеих платформ.
